# Apple Silicon Local Video-Analysis Pipeline: Throughput, Memory and Technique

**Scope note / reliability warning up front.** Hard, reproducible numbers for *4K decode throughput* and for *vision-embedding throughput* on named M-series chips are much scarcer than one would hope. Encode benchmarks are plentiful; pure-decode benchmarks are rare because almost nobody measures decode in isolation. Several figures that circulate in search summaries could not be traced to a primary source on fetch — those are explicitly marked **[UNVERIFIED]** below and should not be used as design inputs without local measurement. Target machine for this research: **M5 Pro MacBook Pro, 48 GB unified memory**. Where a number was measured on M1/M2/M4, that is stated inline; no M1 number is presented as an M5 number.

---

## Q1. Decode throughput for 4K H.264/HEVC/VP9 — VideoToolbox vs software; downscaling; VP9/AV1 generation gating

### Takeaway
The M5 Pro has **exactly one video decode engine** (the M5 Max has one decode engine but two encode engines), hardware-decodes H.264, HEVC, ProRes/ProRes RAW and AV1, and does **not** list VP9 in Apple's spec sheet. The only well-sourced end-to-end 4K figure on a recent chip is **M4: ~380 fps for 4K H.264 decode → 1080p scale → HEVC encode** when the whole pipeline stays inside the media engine, versus **~145 fps for the same work in ffmpeg**, which shuttles frames between the media engine and system memory. That 2.6x gap is the single most important engineering fact here: *the round-trip, not the decode, is usually the bottleneck.*

### Cited Findings

**M5 Pro / M5 Max media engine (the target hardware)**
- M5 Pro media engine: hardware-accelerated **H.264, HEVC, ProRes and ProRes RAW**, plus **AV1 decode**. It has **one video decode engine, one video encode engine, and one ProRes encode/decode engine**. — [Apple, MacBook Pro (14-inch, M5 Pro or M5 Max) Tech Specs](https://support.apple.com/en-us/126318)
- M5 Max has the **same codec list** but **two video encode engines and two ProRes encode/decode engines**. — [Apple Tech Specs](https://support.apple.com/en-us/126318)
- **VP9 is not listed** as a hardware-accelerated codec for either M5 Pro or M5 Max on Apple's spec sheet. — [Apple Tech Specs](https://support.apple.com/en-us/126318)
- M5 Pro unified memory options include **24, 36, 48, 64 and 128 GB** depending on GPU tier; memory bandwidth across the M5 Pro/Max family spans **307 GB/s to 614 GB/s**. — [Apple Tech Specs](https://support.apple.com/en-us/126318)
- Apple's newsroom post states **M5 Pro: up to 64 GB unified memory, 307 GB/s**; **M5 Max: up to 128 GB, 614 GB/s**. This **conflicts** with the spec page's "up to 128 GB" phrasing for the Pro tier — the newsroom figure (64 GB / 307 GB/s for M5 Pro) is the more specific claim. — [Apple Newsroom, "Apple debuts M5 Pro and M5 Max", March 2026](https://www.apple.com/newsroom/2026/03/apple-debuts-m5-pro-and-m5-max-to-supercharge-the-most-demanding-pro-workflows/); vs [Apple Tech Specs](https://support.apple.com/en-us/126318)
- M5 Pro/Max: 18-core CPU (6 "super cores" + 12 performance cores), M5 Pro up to 20-core GPU with a Neural Accelerator in each core, 16-core Neural Engine, **over 4x peak GPU compute for AI versus the prior generation**. — [Apple Newsroom, March 2026](https://www.apple.com/newsroom/2026/03/apple-debuts-m5-pro-and-m5-max-to-supercharge-the-most-demanding-pro-workflows/)

**Measured 4K throughput, chip named**
- **Apple M4**, Tears of Steel, **17,616 frames, 4K H.264 → 1080p HEVC**: HandBrake **~380 fps (46 s total)**; ffmpeg **~145 fps (121 s total)** for the same job. HandBrake keeps data inside the media engine for the whole decode → filter → encode chain; ffmpeg "may shuttle frames between CPU and hardware, creating unnecessary transfers that halve throughput efficiency." Part of HandBrake's advantage is also `kVTCompressionPropertyKey_PrioritizeEncodingSpeedOverQuality` and `kVTCompressionPropertyKey_RealTime`; disabling those flags brought HandBrake in line with ffmpeg. — [HandBrake Discussion #7142](https://github.com/HandBrake/HandBrake/discussions/7142)
- **Apple M2 Pro**, 30-second 4K clip, **encode**: `libx265` software **287 s** vs `hevc_videotoolbox` hardware **12 s** — **~24x**. Hardware output is ~20–30% larger at comparable settings. — [VideoToolbox Hardware Acceleration Guide](https://kcenon.github.io/video_converter/reference/03-videotoolbox-hardware-acceleration/)
- **Entry-level M1** can sustain **three concurrent 4K 24 fps Dolby Vision HEVC 10-bit transcode sessions**. — [VideoToolbox Hardware Acceleration Guide](https://kcenon.github.io/video_converter/reference/03-videotoolbox-hardware-acceleration/)
- **M1 Pro**, H.265 encode: VideoToolbox is **~15x faster than libx265** and handles 4K in real time. — [yre.jp, M1 Pro H.265 hardware encoding benchmark](https://yre.jp/en/post/m1mac_h265/)
- **Apple M4**, 4K capture/stream: `AV_CODEC_FLAG_LOW_DELAY` forces VideoToolbox low-latency rate control and **caps 4K HEVC encode at ~50–55 fps**; without low-latency mode the same 4K HEVC encode reaches **97 fps (10.3 ms/frame)**. — [LizardByte/Sunshine Issue #5814](https://github.com/LizardByte/Sunshine/issues/5814)
- General claim: for codecs the chip supports natively, VideoToolbox decode is **"5–50x faster than software decoding and orders of magnitude more energy-efficient."** This is from a Rust crate's own README, i.e. a secondary and promotional source — treat the range as directional only. — [OxideAV/oxideav-videotoolbox README](https://github.com/OxideAV/oxideav-videotoolbox)

**VP9 and AV1 generation gating**
- AV1 **decode only** (no AV1 hardware encode) on Apple Silicon, available from **M3 onward**; the media engine of M3 and later decodes AV1 and VideoToolbox exposes it "the way it exposes VP9". — [OxideAV/oxideav-videotoolbox README](https://github.com/OxideAV/oxideav-videotoolbox); corroborated for the M4-generation introduction on iPad by [Bitmovin, Apple AV1 Support](https://bitmovin.com/blog/apple-av1-support/)
- AV1 hardware decode on Apple Silicon includes **HDR and DRM support**, and is gated to M3+ with software fallback on older hardware. — [Forasoft, "AV1 in 2026: Hardware Support"](https://www.forasoft.com/learn/video-encoding/articles/av1-state-2026)
- **VP9 is contested.** Third-party sources claim VP9 **profile 0 and profile 2 decode via "Apple's supplemental VideoToolbox decoder" on M1+, with software fallback**. — [OxideAV/oxideav-videotoolbox README](https://github.com/OxideAV/oxideav-videotoolbox); [docs.rs oxideav-videotoolbox](https://docs.rs/crate/oxideav-videotoolbox/latest/source/README.md). **Apple's own M5 Pro/Max spec sheet does not list VP9 at all** — [Apple Tech Specs](https://support.apple.com/en-us/126318). The long-running MacRumors thread on M1 VP9/AV1 decoding reflects the same unresolved disagreement. — [MacRumors, "Apple M1 VP9/AV1 decoding?"](https://forums.macrumors.com/threads/apple-m1-vp9-av1-decoding.2269938/page-4)
- A hardware codec is only reachable through **VideoToolbox or an Apple library built on it**; applications with their own built-in decoders (e.g. a stock libvpx or libdav1d path) will not touch the media engine. — [OxideAV/oxideav-videotoolbox README](https://github.com/OxideAV/oxideav-videotoolbox)

**Downscaling during decode**
- `scale_vt` is the VideoToolbox hardware scaler: it resizes VideoToolbox-decoded frames and converts colour to BT.709 primaries/transfer/matrix; `hwdownload` then brings frames into system memory. — [ffmpeg `vf_scale_vt.c` source](https://ffmpeg.org/doxygen/trunk/vf__scale__vt_8c_source.html); [ffmpeg full documentation](https://www.ffmpeg.org/ffmpeg-all.html)
- **Mixing hardware and software filters in one chain forces frames back and forth between GPU and system memory, which can be slower than staying in software the whole way.** — [Compresto, FFmpeg Scale Filter guide](https://compresto.app/blog/ffmpeg-scale)
- HandBrake historically **disables hardware decoders by default** in preferences, specifically because "the VideoToolbox scaling filter quality has historically been problematic." — [HandBrake Discussion #7142](https://github.com/HandBrake/HandBrake/discussions/7142)

### Inferences
- **The M5 Pro has one video decode engine.** Running N parallel `ffmpeg -hwaccel videotoolbox` processes will contend for that single engine; the M1 result of three concurrent 4K24 HEVC transcodes suggests the per-engine ceiling is roughly "a few times realtime at 4K", not "N× per process". Expect parallel ffmpeg processes to help only until the decode engine saturates, after which the win is zero and the energy cost is real.
- For a *detection* pipeline (decode → downscale → hand frames to Python/OpenCV) the terminal step is always `hwdownload` plus a pixel-format conversion, because NumPy/OpenCV cannot read a `CVPixelBuffer` on the GPU. That means the HandBrake-style "stay in the media engine" optimisation is **not fully available** to this pipeline — the unavoidable download is exactly the cost that made ffmpeg 2.6x slower than HandBrake on M4. The mitigation is to make the downloaded frame as small as possible (`scale_vt` to e.g. 640px before `hwdownload`) and as rare as possible (sample, don't decode every frame).
- Using `scale_vt` *before* `hwdownload` should be strictly better than `hwdownload` then software `scale`, because it cuts the bytes crossing the boundary by the square of the scale factor (4K → 720p is ~9x fewer bytes). No measured figure confirms this on M-series; it follows from the documented filter semantics.
- Order-of-magnitude only, **clearly marked as an estimate**: if M4 sustained ~145 fps for a full ffmpeg 4K-decode + scale + HEVC-encode pipeline, a decode-and-downscale-only pipeline on M5 Pro should comfortably exceed that, so a 1-hour 4K60 recording (~216,000 frames) decoded in full would plausibly take **15–25 minutes**. This is an extrapolation across chip generations and workloads, not a measurement — measure locally before putting it in a time budget.
- Gameplay captures from a PS5 are H.264 or HEVC, both fully hardware-decoded on M5 Pro. VP9/AV1 only matters if footage is re-downloaded from YouTube, in which case **AV1 is safely hardware-decoded on M5 Pro and VP9 is the risky case** — prefer requesting an H.264/AV1 variant over VP9.

### Gaps
- **No isolated 4K decode-only fps benchmark on any M3/M4/M5 chip could be found.** Every published number bundles decode with scale and encode. The frequently-quoted figure "4K HEVC 10-bit: 1.53 s for 600 frames hardware vs 4.40 s software (2.9x), 98% CPU vs 939% CPU" appeared in search summaries but **could not be located in the fetched source** — **[UNVERIFIED]**, do not cite.
- No measured figure for the cost of `hwdownload` + `format=bgr24` per 4K frame on any M-series chip.
- No measured figure for `scale_vt` throughput vs software `scale` (swscale) on M-series.
- Whether the M5 Pro's single decode engine can decode 4K HEVC faster than 4K H.264 (or vice versa) is undocumented.
- VP9 hardware decode on M5 Pro is genuinely unresolved in the sources. **Verify locally** with `ffmpeg -hwaccels` and by timing a VP9 file with and without `-hwaccel videotoolbox`.

## Q2. Cost of sampling strategies: every frame vs `fps` filter vs keyframe-only; fastest way to get N evenly spaced frames

### Takeaway
The `fps` filter does **not** save decode work — it decodes every frame and throws most away. The two genuinely cheap strategies are **keyframe-only decoding** (`-skip_frame nokey`) and **input seeking** (`-ss` *before* `-i`, which seeks by keyframe without decoding the intervening GOPs). For N evenly spaced frames from an hour-long 4K file, N separate input-seek invocations is near-instant per frame and is the right default; a single `-skip_frame nokey` pass is the right choice when you want *all* keyframes and don't care about exact timestamps.

### Cited Findings
- **Using the `fps` filter is slow because it needs to decode the entire video**; on long videos "this turns a millisecond operation into a multi-minute wait." — [FFmpeg Scale/extraction guidance](https://compresto.app/blog/ffmpeg-scale); [trekview, "Setting the right frame rate for video extraction using ffmpeg"](https://www.trekview.org/blog/choosing-right-frame-extraction-rate-ffmpeg/)
- **`-ss` before `-i` makes ffmpeg seek the input by keyframe before it starts decoding, which is near-instant even on a two-hour file. `-ss` after `-i` decodes every frame from the start up to the timestamp.** — [trekview](https://www.trekview.org/blog/choosing-right-frame-extraction-rate-ffmpeg/); [techearl, "Extract a Thumbnail or Frame From a Video with ffmpeg"](https://techearl.com/ffmpeg-video-thumbnail)
- For maximum speed, **`-skip_frame nokey` before the input decodes only keyframes**, and `-vsync passthrough` (modern spelling: `-fps_mode passthrough`) avoids duplicated frames. — [trekview](https://www.trekview.org/blog/choosing-right-frame-extraction-rate-ffmpeg/)
- To get a fixed count of evenly spaced frames regardless of length, **compute the rate from the duration** (`fps=N/duration`) or **use the `thumbnail` filter per segment**. — [trekview](https://www.trekview.org/blog/choosing-right-frame-extraction-rate-ffmpeg/)
- The official ffmpeg wiki has a dedicated page for periodic thumbnail extraction (`-vf fps=1/X`). — [ffmpeg wiki, "Create a thumbnail image every X seconds of the video"](https://ffmpeg.org/trac/ffmpeg/wiki/Create%20a%20thumbnail%20image%20every%20X%20seconds%20of%20the%20video)
- Small-file reference points (**640x360 H.264**, hardware not stated): single-frame extraction via input seek "typically completes in under 100 ms" on a 2 GB file; `fps=1` on a 13-second clip finishes "under 1 second." — [ffmpeg-micro, "How to Extract Frames from Video with FFmpeg"](https://www.ffmpeg-micro.com/blog/extract-frames-from-video-ffmpeg)
- **PySceneDetect** sub-samples by an integer downscale factor (2x–5x), applied automatically based on input resolution and overridable with `-d / --downscale`; `--frame-skip N` processes 1/(N+1) of frames (`-fs 1` → 50%, `-fs 2` → 33%, `-fs 3` → 25%) but "severely reduces frame-accurate scene cuts" and should only be used on high-fps material (ideally >60 fps) at values of 1–2. — [PySceneDetect CLI docs](https://www.scenedetect.com/cli/)
- PySceneDetect now publishes accuracy benchmarks and per-detector parameter sweep curves at scenedetect.com/benchmarks. — [PySceneDetect changelog](https://www.scenedetect.com/changelog/)

### Inferences
- **The keyframe interval sets the resolution of the cheap pass.** Game-capture encoders (PS5 share, OBS) typically use a 2-second GOP, so `-skip_frame nokey` on a 1-hour recording yields ~1,800 frames at ~0.5 fps effective sampling. That is plenty for a banner/scoreboard detector that only needs to notice a kill event's few-second window, and it costs roughly 1/120th of the decode work of a full 60 fps decode.
- **`-skip_frame nokey` and `-ss`-per-frame are not interchangeable.** `-skip_frame nokey` gives you *whatever keyframes exist* (irregular spacing, no control over count); N× `-ss` gives you *exactly N timestamps* but snaps each to the nearest preceding keyframe unless you add a short decode window after the seek. If exact timestamps matter (e.g. aligning to a transcript), use `-ss <t-1> -i file -ss 1 -frames:v 1` (coarse input seek, then precise output seek over one second of decode).
- A useful three-tier structure for an hour of 4K: **tier 0** `-skip_frame nokey` single pass (~1,800 frames, cheapest); **tier 1** targeted `-ss` seeks into nominated windows at full frame rate; **tier 2** full-GOP decode only for the handful of windows that become clips.
- The widely repeated claim that **keyframe extraction is "roughly 110x faster than the fps filter (244 vs 2.2 fps)"** appeared in a search summary and **could not be confirmed in the fetched sources** — **[UNVERIFIED]**. The *direction* is well-supported by the mechanism; the magnitude is not citable.

### Gaps
- No published measurement of `-skip_frame nokey` throughput on a 4K file on any M-series chip.
- No published measurement of per-seek overhead for N× `-ss` invocations on 4K (process startup + container index seek + GOP decode), which determines the N at which one full decode pass becomes cheaper than N seeks.
- Whether `-skip_frame nokey` is compatible with `-hwaccel videotoolbox` (i.e. whether frame-skip happens before or after the hardware decoder is handed the bitstream) is not documented in any source found.

## Q3. Model speeds on M-series: Whisper, CLIP/SigLIP/DINOv3, audio event models, small video-LMs

### Takeaway
**Whisper is effectively free** at this scale: the best-sourced figure is **55x realtime for large-v3-turbo on M4 Max**, i.e. an hour of audio in roughly a minute, and Parakeet-via-CoreML is ~5x faster still. **Image embedding is the real budget line**, and the numbers span three orders of magnitude depending on model size and whether the Neural Engine is used — from **~6 img/s for CLIP ViT-H-14 on M1** to **~1150 img/s for CLIP on M4 Pro with ANE+GPU**. **Audio event models (PANNs/AST) have no published macOS benchmark at all**, and **DINOv3 has no published Apple Silicon speed benchmark at all.**

### Cited Findings

**Whisper / ASR — chip named**
- **MacBook Pro M4 Max, 128 GB**, 46.7-second audio sample, MLX stack: `whisper-tiny` **0.24 s (197x RTF)**; `whisper-small` **0.47 s (98x RTF)**; `whisper-large-v3-turbo` **0.86 s (55x RTF)**. — [vllm-mlx audio benchmarks](https://github.com/waybarrios/vllm-mlx/blob/main/docs/benchmarks/audio.md)
- **MacBook Pro M4, 24 GB**, large-class models, average time per sample (shorter is better): `fluidaudio-coreml` (parakeet-tdt-0.6b-v2-coreml) **0.1935 s**; `parakeet-mlx` **0.4995 s**; `mlx-whisper` (large-v3-turbo) **1.0230 s**; `insanely-fast-whisper` (large-v3-turbo) **1.1324 s**; `whisper.cpp` (large-v3-turbo-q5_0) **1.2293 s**; `lightning-whisper-mlx` (large) **1.8160 s**; `whisperkit` (large-v3) **2.2190 s**; `whisper-mps` (large) **5.3722 s**; `faster-whisper` (large-v3-turbo) **6.9613 s**. The same repo notes FluidAudio reaching **~110x RTF on M4 Pro**. — [anvanvan/mac-whisper-speedtest](https://github.com/anvanvan/mac-whisper-speedtest)
- `whisper.cpp` on Apple Silicon: inference runs **fully on the GPU via Metal**; the **Core ML encoder on the ANE is "more than x3 faster compared with CPU-only execution"**; **ANEForge is "about 2x faster than the Core ML encoder from tiny to medium."** — [ggml-org/whisper.cpp README](https://github.com/ggml-org/whisper.cpp)
- `whisper.cpp` memory footprint per model: tiny 75 MiB disk / ~273 MB RAM; base 142 MiB / ~388 MB; small 466 MiB / ~852 MB; medium 1.5 GiB / ~2.1 GB; large 2.9 GiB / ~3.9 GB. — [ggml-org/whisper.cpp README](https://github.com/ggml-org/whisper.cpp)
- **Conflicting, lower-quality claim:** "large-v3 hits roughly 2 to 3x realtime on an M3 or M4 with Metal," i.e. a one-minute clip in 20 seconds. — [promptquorum, "Whisper STT on Apple Silicon 2026"](https://www.promptquorum.com/local-llms/apple-silicon-whisper-metal-benchmark); [justvoice.ai, "Whisper benchmark on Apple Silicon"](https://justvoice.ai/blog/whisper-benchmark-apple-silicon-m3-m4). **This is ~20x slower than the vllm-mlx M4 Max figure.** Both are plausible because they are different models — `large-v3` has 32 decoder layers while `large-v3-turbo` has 4 — but both pages are SEO-style aggregators with no stated methodology, so weight the vllm-mlx and mac-whisper-speedtest repos (which publish harnesses) far more heavily.
- Independent cross-check from a user report: MLX Whisper achieved a **21.0x realtime multiplier vs WhisperX's 5.2x** on the same audio (58.7 s vs 237.2 s), chip not stated. — [note.com, "20-Minute Meeting Transcribed in 58 Seconds"](https://note.com/micnote/n/n84a1f1492c02?hl=en)

**Image embedding — chip named**
- **M1**, CLIP **ViT-H-14**: Core ML **~6 image embeddings/s** vs PyTorch+MPS **~1.5 img/s** — Core ML is **~4x faster than torch+mps** for the same model. — [damian0815/CLIP-ViT-H-14-laion2B-s32B-b79K_CoreML model card](https://huggingface.co/damian0815/CLIP-ViT-H-14-laion2B-s32B-b79K_CoreML)
- **M4 Pro**: CLIP reaches **~1150 images/s with the Neural Engine running alongside the GPU**, vs **~600 images/s GPU-alone** (~1.9x). Same source: EmbeddingGemma 2 via MLX+ANE **~8 img/s** vs PyTorch-alone **~2.5 img/s** (~3x). **Caveat:** the CLIP variant is not named (1150 img/s is only plausible for a ViT-B/32-class model), and the PyPI page failed to load on fetch so this is a **search-summary-only citation** — treat as directional. — [panopticml 1.0.0 on PyPI](https://pypi.org/project/panopticml/1.0.0/)
- MLX has a community CLIP wrapper (`mlx_clip`) for Apple Silicon, but the repo publishes no throughput figures. — [harperreed/mlx_clip](https://github.com/harperreed/mlx_clip)

**M5-generation ML uplift (Apple's own measurements)**
- **MacBook Pro with M5, 24 GB**, MLX: **time-to-first-token up to 4x faster than M4**; TTFT under 10 s for 14B dense models and under 3 s for 30B MoE models; **subsequent-token generation only 1.19x–1.27x faster** (19–27%). Memory bandwidth **M4 120 GB/s → M5 153 GB/s (+28%)**. FLUX-dev-4bit (12B) generates 1024x1024 images **3.8x faster on M5**. Apple's explanation: "First token generation is compute-bound and fully takes advantage of the Neural Accelerators," while "subsequent tokens are bounded by memory bandwidth rather than compute ability." — [Apple ML Research, "Exploring LLMs with MLX and the Neural Accelerators in the M5 GPU"](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)

**Small video-language models**
- **Qwen2.5-VL-32B 4-bit on Mac Studio**: prompt (prefill) throughput **111.985 tok/s**, generation throughput **17.328 tok/s**. Exact chip (M3 Ultra configuration) is reported in the surrounding article; the tok/s figures are the citable part. — [MacStories, "Notes on Early Mac Studio AI Benchmarks"](https://www.macstories.net/notes/notes-on-early-mac-studio-ai-benchmarks-with-qwen3-235b-a22b-and-qwen2-5-vl-72b/)
- Also reported: **Qwen2.5-VL-32B 4-bit at 111.985 tok/s prefill / 17.328 tok/s generation**, cross-referenced by [Simon Willison on Qwen2.5-VL-32B](https://simonwillison.net/2025/Mar/24/qwen25-vl-32b/)
- **M4 Max**: vLLM-MLX reaches **up to 525 tokens/s for small models**. — [waybarrios/vllm-mlx](https://github.com/waybarrios/vllm-mlx/blob/main/docs/benchmarks/audio.md)
- `mlx-vlm` is the maintained package for VLM inference and fine-tuning on Mac via MLX and supports Qwen2-VL / Qwen2.5-VL. — [Blaizzy/mlx-vlm](https://github.com/Blaizzy/mlx-vlm)

**Audio event models (PANNs, AST)**
- AudioSet mAP reference: **PANNs (CNN era, 2020) 0.431 mAP; AST (pure transformer, 2021) 0.485 mAP**. — [Geo-ATBench paper](https://arxiv.org/pdf/2603.10623)
- **Only on-device timing found is non-Apple:** PANNs **CNN14 on Pixel 8a GPU ≈ 124 ms inference + ~99 ms host log-mel ≈ 0.22 s per 10-second clip** (≈45x realtime). — [google-ai-edge/litert-samples PR #184](https://github.com/google-ai-edge/litert-samples/pull/184)
- PANNs architectures, **particularly Wavegram_Logmel and CNN14, consistently exhibit higher inference times and CPU temperatures**, making them less suitable for real-time or resource-constrained use. — [arXiv 2509.14049, "Comprehensive Evaluation of CNN-Based Audio Tagging Models on Resource-Constrained Devices"](https://arxiv.org/html/2509.14049v1)
- Under a common AudioSet→benchmark label mapping, **PANNs scored best, then CLAP, with AST worst** — accuracy ranking, not speed. — [Geo-ATBench](https://arxiv.org/pdf/2603.10623)

### Inferences
- **Audio-first is the right cheap signal.** At 55x RTF on M4 Max, large-v3-turbo transcribes an hour in **~65 seconds** (3600/55); Parakeet-CoreML at ~110x RTF on M4 Pro does it in **~33 seconds**. Both are trivial next to any per-frame vision pass. For a kill-clip detector, extracting the audio track (`-vn -acodec pcm_s16le`) and running Parakeet or whisper-large-v3-turbo over the whole hour costs about a minute and gives a fully indexed timeline for free.
- **Embedding cost dominates and is entirely a function of model choice.** Using the two anchors: at **~6 img/s (ViT-H-14 Core ML on M1)**, 1,800 keyframes takes **5 minutes** and 216,000 full-rate frames takes **10 hours** — the latter is disqualifying. At **~600–1150 img/s (CLIP on M4 Pro, GPU / GPU+ANE)**, 1,800 keyframes takes **2–3 seconds** and even 216,000 frames takes **3–6 minutes**. The design conclusion is blunt: **use a ViT-B-class model and the ANE, and the vision pass stops being the bottleneck**; use a ViT-H/giant model and you must sample aggressively.
- **M5 Pro should be meaningfully better than M4 Pro on exactly this workload.** Apple's own M5 data shows the Neural Accelerators help *compute-bound* work (4x on prefill) far more than *bandwidth-bound* work (1.2x on generation). Batched image embedding is compute-bound and shape-static — it is the best-case profile for the per-core Neural Accelerators and for the "over 4x peak GPU compute for AI" claim. No M5 Pro embedding benchmark exists, but the mechanism argues the M4 Pro CLIP figures are a conservative floor.
- **The PyTorch-MPS penalty is large and consistent across sources**: ~4x on M1 (Core ML vs torch+mps, ViT-H-14) and ~3x on M4 Pro (MLX+ANE vs PyTorch, EmbeddingGemma 2). Shipping the embedding model through PyTorch MPS wastes roughly two-thirds to three-quarters of the machine. Convert to Core ML (or MLX) for the hot path.
- **A video-LM is a tier-2 tool only.** At ~17 tok/s generation for a 32B 4-bit VLM, a 100-token verdict per candidate window costs ~6 s plus prefill. That is fine for 20–50 nominated windows (2–5 minutes total) and impossible for thousands.

### Gaps
- **No published image-embedding throughput figure on any M5-generation chip** for CLIP, SigLIP, SigLIP 2 or DINOv3. The M4 Pro figures are the most recent available.
- **No SigLIP or SigLIP 2 throughput benchmark on Apple Silicon** was found at all.

## Q4. Memory limits and gotchas on a 48 GB machine

### Takeaway
There is a **directly relevant primary source measured on a 48 GB M5 Pro Mac**: `torch.mps.recommended_max_memory()` returns **37.44 GiB**, and PyTorch's **default high watermark ratio of 1.7 sets the OOM ceiling at 63.6 GiB — above the machine's physical RAM**. The practical consequence is that PyTorch on this exact machine will **swap to disk rather than raise an OOM error**, which looks like a mysterious system-wide stall instead of a clean failure. Setting the ratio to **0.8 (29.95 GiB)** restores graceful failure.

### Cited Findings
- On a **48 GB M5 Pro Mac**, `torch.mps.recommended_max_memory()` returns **37.44 GiB**. — [dev.to/nefayran, "MPS backend out of memory on a Mac: what the numbers mean and how to set the watermark"](https://dev.to/nefayran/mps-backend-out-of-memory-on-a-mac-what-the-numbers-mean-and-how-to-set-the-watermark-43dp)
- The hard cap is `max_allowed = PYTORCH_MPS_HIGH_WATERMARK_RATIO × torch.mps.recommended_max_memory()`. **Default high ratio is 1.7**, which on this 48 GB machine is **63.6 GiB** — i.e. the limit exceeds physical RAM, so "processes swap into disk storage before hitting PyTorch's error." — [dev.to/nefayran](https://dev.to/nefayran/mps-backend-out-of-memory-on-a-mac-what-the-numbers-mean-and-how-to-set-the-watermark-43dp)
- **Default low watermark ratio is 1.4** on Apple Silicon (a soft limit tied to "adaptive commit and garbage collection"), and it **cannot exceed the high ratio** unless the high ratio is 0.0. **Setting only the high ratio fails at the first MPS call with "invalid low watermark ratio 1.4"** — both env vars must be set together, and **before the first tensor reaches MPS**. — [dev.to/nefayran](https://dev.to/nefayran/mps-backend-out-of-memory-on-a-mac-what-the-numbers-mean-and-how-to-set-the-watermark-43dp)
- `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0` "disables upper limit for memory allocations (may cause system failure)"; in testing it **produced no observable change — the system still swapped before reaching any error**. — [dev.to/nefayran](https://dev.to/nefayran/mps-backend-out-of-memory-on-a-mac-what-the-numbers-mean-and-how-to-set-the-watermark-43dp); the same `0.0` advice (and warning) appears in [PyTorch Forums, "MPS backend out of memory"](https://discuss.pytorch.org/t/mps-backend-out-of-memory/183879)
- On the 48 GB test machine, **ratios of 0.8 (29.95 GiB) and 0.5 (18.72 GiB) prevented swap entirely**, with 0.8 "performing cleanly… enabling graceful failure with opportunity to adjust batch sizes rather than system-wide slowdown from swapping." Advice: set ratios "below the memory your Mac really has free, with your usual apps open." — [dev.to/nefayran](https://dev.to/nefayran/mps-backend-out-of-memory-on-a-mac-what-the-numbers-mean-and-how-to-set-the-watermark-43dp)
- MPS raises `NotImplementedError` for operators it lacks; reported examples include **`aten::cumsum.out` and `aten::upsample_linear1d.out`**. — [PyTorch Forums MPS OOM/op threads](https://discuss.pytorch.org/t/mps-backend-out-of-memory/183879). The umbrella tracking issue for MPS operator coverage is [pytorch/pytorch#77754](https://github.com/pytorch/pytorch/issues/77754). *(Note: individual operators in these old reports may since have landed; check against your installed version rather than assuming the reports are current.)*
- MPS has **three implementation paths per op: link to an existing MPS op, write a custom Metal kernel, or fall back to CPU**; CPU fallback is configured in `MPSFallback.mm`. — [pytorch/pytorch wiki, MPS Backend](https://github.com/pytorch/pytorch/wiki/MPS-Backend)
- **MPS kernels do not natively support strided tensor access**, so view operations (slicing, permutation) go through a **"Gather-Scatter approach"** — an implicit materialisation cost on non-contiguous tensors. — [pytorch/pytorch wiki, MPS Backend](https://github.com/pytorch/pytorch/wiki/MPS-Backend)
- Profiling hooks exist: `torch.mps.profiler.start()` / `.stop()`, OS Signposts, Xcode Instruments integration. — [pytorch/pytorch wiki, MPS Backend](https://github.com/pytorch/pytorch/wiki/MPS-Backend)
- Some MPS OOM issues were reported fixed in **PyTorch 2.3.0.dev**. — [PyTorch Forums](https://discuss.pytorch.org/t/mps-backend-out-of-memory/183879); related: [pytorch/pytorch#105839](https://github.com/pytorch/pytorch/issues/105839)
- Real-world Qwen2-VL-7B MPS memory failures are documented on the model's HF discussion board. — [Qwen2-VL-7B-Instruct discussion #8](https://huggingface.co/Qwen/Qwen2-VL-7B-Instruct/discussions/8)
- Practical MPS failure modes in a real vision app (ComfyUI on Mac) are catalogued with fixes. — [localaimaster, "ComfyUI on Mac: MPS Errors and What Fixes Them"](https://localaimaster.com/blog/comfyui-mps-errors-mac)

**MLX vs Core ML tradeoffs**
- **The Apple Neural Engine is not generally exposed for arbitrary custom compute. Core ML may target it; research frameworks (including MLX) typically run on GPU and CPU.** — [rockyshikoku, "Apple Core AI vs MLX"](https://rockyshikoku.medium.com/apple-core-ai-vs-mlx-which-is-faster-on-iphone-and-mac-for-the-same-model-8faf3c8784ff)
- Choose **Core ML / Core AI** when you want Apple's own export and runtime, an **ANE path with static shapes**, ahead-of-time compilation, hardware specialisation and Xcode tooling. Choose **MLX** when you want any Hugging Face checkpoint today, the largest quantized-model catalogue, a Python dev loop, direct control over unified memory, and the best Mac energy Pareto. — [rockyshikoku](https://rockyshikoku.medium.com/apple-core-ai-vs-mlx-which-is-faster-on-iphone-and-mac-for-the-same-model-8faf3c8784ff); [murmurtts, "Apple Core AI vs MLX for Local Mac Models"](https://www.murmurtts.com/blog/apple-core-ai-vs-mlx-local-models-mac)
- Memory footprint differs sharply by runtime: on **iPhone 17 Pro with Qwen3-0.6B**, CoreML-LLM used **184 MB — about 6x leaner than Core AI's ANE path**; throughput was Core AI pipelined-GPU **193.3 tok/s cold** vs MLX **167.2 cold / 158.8 warm**. **iPhone, not Mac** — use for the qualitative tradeoff only. — [rockyshikoku](https://rockyshikoku.medium.com/apple-core-ai-vs-mlx-which-is-faster-on-iphone-and-mac-for-the-same-model-8faf3c8784ff)
- A reproducible cross-runtime harness (Core AI, MLX, llama.cpp, LiteRT-LM, Core ML on the same model, every number with its quantization) exists for **iPhone 17 Pro and M4 Max**. — [john-rocky/apple-silicon-llm-bench](https://github.com/john-rocky/apple-silicon-llm-bench)

### Inferences
- **Set both watermark env vars explicitly, before importing torch**, e.g. `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.8` and `PYTORCH_MPS_LOW_WATERMARK_RATIO=0.6`. On a 48 GB machine this caps PyTorch at ~30 GiB, which fails loudly instead of swapping. Setting only the high ratio is a hard error at the first MPS call.
- **Budget on ~37 GiB, not 48 GB.** `recommended_max_memory()` already discounts what macOS reserves. With Safari/IDE open, realistic working headroom for a long-running pipeline is closer to **25–30 GiB**, and that must cover the decoded frame buffers, the embedding model, and the growing embedding array simultaneously.
- **The swap-instead-of-OOM behaviour is the single nastiest failure mode for a multi-hour job.** A pipeline that silently starts paging will appear to be "still running" while throughput drops by an order of magnitude — exactly the symptom that is easy to misdiagnose as a slow model. Instrument wall-clock-per-window and bail if it degrades.
- **Gather-Scatter on strided tensors is a quiet tax** specific to MPS. Call `.contiguous()` before handing batched frame tensors to the model, and avoid building batches by fancy-indexing a large tensor on-device.
- **Runtime choice follows the ANE question.** The ANE is only reachable through Core ML, and the M4 Pro figures show ANE+GPU at ~1.9x GPU-alone for CLIP. For a fixed-shape, batched embedding pass — the archetypal static-shape workload — Core ML is the right runtime. MLX is the right runtime for the ASR and VLM stages, where model variety and quantization catalogue matter more than ANE access.

### Gaps
- No official Apple documentation was found stating how much unified memory macOS reserves from the GPU, or the formula behind `recommended_max_memory()` across RAM sizes. The 48 GB → 37.44 GiB data point is a single community measurement (though on exactly the target chip).
- No current, authoritative list of MPS-unsupported operators was found; the wiki is a contributor guide and the forum reports are version-specific. Verify against the installed PyTorch.
- No measured figure for the throughput cost of `PYTORCH_ENABLE_MPS_FALLBACK=1` (CPU round-trip per fallback op) on any M-series chip.
- No Mac-measured Core ML vs MLX memory-footprint comparison was found — the 6x figure is from iPhone 17 Pro.

## Q5. Practical techniques that keep an hour tractable

### Takeaway
Three techniques carry most of the weight, and all three are supported by the evidence above: **(1) don't cross the GPU/CPU boundary more than necessary** — the M4 HandBrake-vs-ffmpeg result shows round-tripping halves throughput; **(2) cascade from a cheap keyframe/audio pass to an expensive model on nominated windows only** — the cheap pass costs ~1/120th of a full decode; **(3) use the ANE with static batch shapes** — worth ~1.9x on M4 Pro for CLIP, and 3–4x versus PyTorch MPS. Parallel ffmpeg processes are the *weakest* lever on M5 Pro, because the chip has only one video decode engine.

### Cited Findings
- **Keep frames inside the media engine.** HandBrake maintains data within the Media Engine throughout decode → filter → encode, whereas ffmpeg "may shuttle frames between CPU and hardware, creating unnecessary transfers that halve throughput efficiency" — **380 fps vs 145 fps on M4** for the same 4K job. — [HandBrake Discussion #7142](https://github.com/HandBrake/HandBrake/discussions/7142)
- **Mixing hardware and software filters in one chain forces frames back and forth and can be slower than staying in software the whole way.** — [Compresto, FFmpeg Scale Filter](https://compresto.app/blog/ffmpeg-scale)
- **Parallel decode has a hard ceiling set by the engine count.** The M5 Pro has **one video decode engine**; the M5 Max also has one decode engine (its second engine is for encode). — [Apple Tech Specs](https://support.apple.com/en-us/126318). An entry-level **M1** sustained **three concurrent 4K24 HEVC 10-bit sessions**, which gives a sense of per-engine headroom. — [VideoToolbox Hardware Acceleration Guide](https://kcenon.github.io/video_converter/reference/03-videotoolbox-hardware-acceleration/)
- **Downscale and frame-skip are first-class knobs** in mature tooling: PySceneDetect auto-downscales by resolution and exposes `-d`, and `--frame-skip N` cuts processed frames to 1/(N+1) with an explicit accuracy warning. — [PySceneDetect CLI docs](https://www.scenedetect.com/cli/)
- **Cheap-signal-nominates-windows is the design used by shipping local tools.** VideoHighlighter "scores strong moments from scene, motion, audio, objects, actions and the transcript, shows why each one scored on a signal timeline and in a report, then exports a highlight reel and the individual clips." — [wj4616/VideoHighlighter](https://github.com/wj4616/VideoHighlighter)
- **ANE requires static shapes.** The Core ML/Core AI path is the one with "a Neural Engine path with static shapes" and ahead-of-time compilation; MLX gives "direct control over Apple Silicon unified memory" but runs on GPU/CPU. — [rockyshikoku, Core AI vs MLX](https://rockyshikoku.medium.com/apple-core-ai-vs-mlx-which-is-faster-on-iphone-and-mac-for-the-same-model-8faf3c8784ff)
- **Running the ANE alongside the GPU, rather than instead of it, is the win:** CLIP **~1150 img/s with ANE next to GPU vs ~600 img/s GPU-alone on M4 Pro** (~1.9x). **[Search-summary citation; page failed to fetch.]** — [panopticml on PyPI](https://pypi.org/project/panopticml/1.0.0/)
- **Compute-bound stages benefit most from M5's Neural Accelerators** (4x on prefill) while bandwidth-bound stages barely move (1.19–1.27x on token generation). — [Apple ML Research, MLX on M5](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)
- **Encoder-side flags matter for the clip-export stage:** `PrioritizeEncodingSpeedOverQuality` + `RealTime` accounted for much of HandBrake's 2.6x advantage on M4. — [HandBrake Discussion #7142](https://github.com/HandBrake/HandBrake/discussions/7142). Conversely, `AV_CODEC_FLAG_LOW_DELAY` **caps 4K HEVC encode at ~50–55 fps on M4** versus 97 fps without it — do not set low-delay for offline clip export. — [Sunshine Issue #5814](https://github.com/LizardByte/Sunshine/issues/5814)
- **Input seeking is the cheap way into a candidate window:** `-ss` before `-i` is "near-instant even on a two-hour file." — [trekview](https://www.trekview.org/blog/choosing-right-frame-extraction-rate-ffmpeg/)

### Inferences
- **Single pipe beats parallel processes on M5 Pro for the decode-bound stage**, because N processes contend for one decode engine while each pays its own `hwdownload` and process-startup cost. Parallelism is better spent *across stages* (decode feeding a queue while the embedder drains it) than *across decoder instances*. The place parallel ffmpeg processes genuinely win is the **tier-1 seek phase**, where each process does a near-instant seek and a tiny decode, so per-process overhead dominates over engine contention.
- **A concrete three-tier budget for a 1-hour 4K60 recording on M5 Pro** (component figures cited above; the composition is inference, and the M4/M1 provenance of the components means these are order-of-magnitude, not measured):
  - Tier 0a — audio: demux + Parakeet-CoreML/whisper-turbo over the full hour → **~30–70 s**
  - Tier 0b — keyframes: one `-skip_frame nokey` pass with `scale_vt` → ~1,800 frames at ≤720p, plus a ViT-B-class Core ML embedding pass at 600–1150 img/s → **a few seconds of model time**, dominated by the decode pass itself
  - Tier 1 — nominated windows: ~30–60 windows × `-ss` seek + 3 s full-rate decode (~180 frames each) → **~10,000 frames**, seconds of model time
  - Tier 2 — adjudication: a small VLM at ~17 tok/s generation over 30–60 windows → **3–7 minutes**
  - The structural point: **Tier 2 is the budget**, and it is bounded by *how many windows Tier 0 nominates*, not by the length of the video. Tune Tier 0's threshold to hold the window count fixed, and total runtime becomes roughly independent of recording length.
- **Cache embeddings keyed on (file content hash, timestamp, model id, preprocessing params).** Every source above shows the expensive part is the model pass, and detector iteration (the user's stated workflow of validating on short cuts before full runs) re-runs the same frames repeatedly. Caching converts iteration cost from minutes to zero.
- **Memory-map the embedding array.** 216,000 frames × 512 float32 dims is only ~440 MB, so an hour at full frame rate fits in RAM comfortably — but 20 hours of footage at ViT-L dimensionality (1024 dims) is ~17 GB, which against a **~37 GiB PyTorch ceiling** is the point where `numpy.memmap` or a float16 store stops being optional. Store float16 by default: it halves the footprint at negligible retrieval-quality cost for nearest-neighbour search.
- **Fix the batch shape.** Since the ANE path requires static shapes, pad the final partial batch rather than letting it recompile; a variable-shape batch silently drops off the ANE and onto the GPU, forfeiting the ~1.9x.

### Gaps
- **No measured figure for parallel-ffmpeg scaling on any M3/M4/M5 chip** (the M1 three-session figure is the only data point, and it is for transcode, not decode-only).
- No Mac-specific published guidance or measurement on **memory-mapped arrays / `numpy.memmap` throughput for embedding stores** — the recommendation above is general practice, not a cited Apple Silicon finding.
- No measurement of **single-pipe (`ffmpeg … -f rawvideo pipe:1` into Python) throughput vs writing JPEGs to disk** on any M-series chip. This is a genuinely important unknown: pipe overhead vs filesystem overhead at 4K is not documented.
- No published measurement of the **recompilation cost of a variable-shape Core ML batch** on M-series.

## Q6. Documented end-to-end examples of analysing hours of video locally on a Mac, with timings

### Takeaway
**There is no rigorous, independently reproduced end-to-end benchmark of a multi-hour local Mac video-analysis pipeline.** The only timings found are **self-reported in a project's own README** (M1 Pro, 62-minute 1080p in ~90 s; 2-hour 4K in ~4–6 min), from a repository that appears in at least three identical forks with no published methodology. This is the largest gap in the research and the strongest argument for calibrating the time budget on the user's own PS5 footage rather than on any published figure.

### Cited Findings
- **VideoHighlighter** (local, Ollama-powered, cross-platform) self-reports: a **62-minute 1080p interview on an M1 Pro took about 90 seconds** for local analysis and returned 10 clip suggestions; a **2-hour 4K webinar on the same Mac took about 4–6 minutes** and surfaced 10–12 strong moments; in **simple mode (no AI) a 1-hour video often takes around 20 minutes on a typical CPU**; with **AI mode, transcription and people detection enabled, an hour of footage can take well over an hour**. — [wj4616/VideoHighlighter](https://github.com/wj4616/VideoHighlighter)
- **Source-quality warning:** the identical README and identical numbers appear across at least three separate GitHub accounts — [wj4616/VideoHighlighter](https://github.com/wj4616/VideoHighlighter), [CMCORPUSG/VideoHighlighter](https://github.com/CMCORPUSG/VideoHighlighter), [Aseiel/VideoHighlighter](https://github.com/Aseiel/VideoHighlighter) — with no stated hardware configuration beyond "M1 Pro", no model versions, and no description of what "analysis" included. Treat as a vendor claim, not a benchmark.
- The same project notes the realistic use case for long footage: for CCTV or trail-camera material, **object detection plus motion can find the minutes something moved across hours of footage locally**, with nothing uploaded. — [wj4616/VideoHighlighter](https://github.com/wj4616/VideoHighlighter)
- A **reference implementation of VLM-based highlight generation** exists and is readable: the SmolVLM2 HighlightGenerator Space's `app.py`. It runs on Hugging Face hardware, so **no Mac timing is attached**, but it documents a working frame-sampling → VLM → highlight-selection flow. — [HuggingFaceTB/SmolVLM2-HighlightGenerator app.py](https://huggingface.co/spaces/HuggingFaceTB/SmolVLM2-HighlightGenerator/blob/524fae70a17b87a87c8f1ad20425425febd003e0/app.py)
- Reproducible-harness precedent exists for the *model* half of the problem on named Apple chips — [anvanvan/mac-whisper-speedtest](https://github.com/anvanvan/mac-whisper-speedtest) (M4), [waybarrios/vllm-mlx](https://github.com/waybarrios/vllm-mlx/blob/main/docs/benchmarks/audio.md) (M4 Max), [john-rocky/apple-silicon-llm-bench](https://github.com/john-rocky/apple-silicon-llm-bench) (M4 Max, iPhone 17 Pro) — but none of these covers the decode or sampling half.
- Academic highlight-detection work (weakly-supervised, learning from video duration) exists but reports accuracy on datasets, not local-Mac wall-clock. — [Xiong et al., "Less is More: Learning Highlight Detection from Video Duration", CVPR 2019](https://www.cs.utexas.edu/~grauman/papers/CVPR19_highlights.pdf)

### Inferences
- The VideoHighlighter spread — **90 s for an hour in one mode, "well over an hour" for an hour in another** — is a ~40x range for the same input, and it maps exactly onto the cascade argument: the fast mode is cheap signals on sampled frames; the slow mode runs transcription plus a per-frame detector. Even as an unverified source, it corroborates that **the mode of operation, not the hardware, determines whether an hour is 90 seconds or 90 minutes.**
- Because no published end-to-end figure is trustworthy and no isolated 4K decode-only M5 figure exists, **the time budget must be established by local measurement.** The minimum useful calibration set, matching the user's existing "test on small segments" practice: (a) time `-skip_frame nokey` + `scale_vt` + `hwdownload` over a 5-minute cut and extrapolate linearly in frames; (b) time 1,000 embeddings at the chosen batch size and model; (c) time the ASR pass on 5 minutes of audio; (d) time one tier-2 VLM call. Those four numbers plus a nominated-window count produce a defensible budget for any recording length — all four are cheap to obtain and none of them can be substituted from the literature.

### Gaps
- **No independently reproduced end-to-end Mac video-analysis timing exists at all.** Every end-to-end figure found is self-reported by the tool's author.
- No end-to-end example was found on **any M3/M4/M5-generation chip** — the only end-to-end numbers are M1 Pro.
- No end-to-end example was found for **gameplay footage specifically** (high motion, HUD-heavy, 60 fps), which is materially different from the interview and webinar material in the one available source.
- No source reports **peak memory** for an end-to-end multi-hour local run, so the headroom analysis in Q4 cannot be validated against a real pipeline.
